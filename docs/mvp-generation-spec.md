# Система процедурной генерации мира

## 1. Цели и требования

### 1.1. Назначение

Обеспечить создание процедурно сгенерированного 2D-мира, который является основой для игрового процесса. Мир должен быть пригоден для исследования, добычи ресурсов, крафта и сражений в рамках MVP. Генерация должна быть детерминированной (по сиду), масштабируемой и архитектурно готовой к будущему расширению (новые биомы, структуры, чанки, мультиплеер).

### 1.2. Требования к миру (MVP)

- **Размер:** 200 тайлов по горизонтали (X) и 100 по вертикали (Y).  
- **Глубина:** Поверхность (средняя высота Y ≈ 20), пещеры (Y ≈ 50–85), нижняя граница из камня (Y ≈ 85–99).  
- **Биомы:** два подбиома - **Лес** (поверхность) и **Пещеры** (подземелье). Они чередуются горизонтально (несколько участков леса и подземных пещер под ними).  
- **Ресурсы:** Древесина (из деревьев), земля с травой (`GRASS`), земля без травы (`DIRT`), камень (`STONE`), медная руда (`COPPER_ORE`).  
- **Растительность:** Деревья только на `GRASS`, плотность регулируется.  
- **Разломы:** 3 штуки, только в пещерах (разные X, глубина).  
- **Враги:** пока не генерируются (спавнятся отдельной системой), но мир должен предусматривать места для спауна (поверхность и пещеры).  
- **Макробиомы:** Свет и Тьма. Единая карта блоков, два `TileMapLayer` с разными атласами. Изменения в одном макробиоме синхронно применяются к другому.

### 1.3. Принципы разработки

- **Данные - в Resource** (`BiomeData`).  
- **Строгая типизация** (использовать `StringName` для идентификаторов).  
- **Композиция** - система генерации строится из независимых компонентов (генератор высоты, генератор пещер, генератор руд и т.д.).  
- **Масштабируемость** - поддержка чанков (16×16) с самого начала; все операции с картой идут через `ChunkManager`.  
- **Подготовка к мультиплееру** - единая карта (в чанках), сервер управляет генерацией и рассылает изменения.

## 2. Архитектура генерации

### 2.1. Основные классы (Autoload / синглтоны)

| Класс | Назначение |
|---|---|
| `WorldGenerator` | Главный контроллер генерации. Запускает поэтапную генерацию, управляет прогресс-баром. |
| `WorldManager` | Хранит текущее состояние мира (ссылки на чанки, `TileMapLayer`), управляет переключением макробиомов. |
| `BiomeRegistry` | Загружает все `BiomeData` из `resources/biomes/` и предоставляет доступ по `id`. |
| `ChunkManager` | Управляет чанками (загрузка/выгрузка, доступ по координатам, dirty-флаги). В MVP загружает все чанки сразу. |
| `SaveManager` | Сохраняет и загружает мир (сид, чанки, инвентарь, позиция игрока, текущий макробиом). |

### 2.2. Ресурсы

#### `BiomeData` (`.tres`)

```gdscript
class_name BiomeData extends Resource

@export var id: StringName = &""               # уникальный идентификатор, например "biome.forest_surface"
@export var display_name: String = ""          # для отладки
@export var biome_type: BiomeType              # enum { SURFACE, UNDERGROUND }

# Диапазон высот, где этот биом может появляться (глобальные Y)
@export var height_range: Vector2 = Vector2(0, 0)   # (min_y, max_y)

# Тайлы для разных слоев (ссылки на источники в TileSet)
@export var surface_tile: TileSetAtlasSource   # трава (GRASS)
@export var subsoil_tile: TileSetAtlasSource   # земля (DIRT)
@export var stone_tile: TileSetAtlasSource     # камень (STONE)
@export var ore_tile: TileSetAtlasSource       # руда (COPPER_ORE) - опционально

# Параметры размещения объектов
@export var tree_density: float = 0.0          # вероятность дерева на блоке GRASS (0..1)
@export var ore_density: float = 0.0           # вероятность руды в пещерах (0..1)
@export var min_cluster_size: int = 2          # минимальный размер жилы
@export var max_cluster_size: int = 5          # максимальный размер жилы
```

#### Идентификаторы тайлов (enum)

```gdscript
enum TileID {
    AIR = 0,
    GRASS = 1,
    DIRT = 2,
    STONE = 3,
    COPPER_ORE = 4,
    WOOD = 5,        # ствол дерева (условный тайл)
    LEAVES = 6,      # листва (условный тайл)
}
```

> В карте (чанках) используются **целочисленные идентификаторы** (`int`). Маппинг к реальным тайлам в `TileSet` выполняется через отдельные функции (см. раздел 4).

### 2.3. Глобальные данные мира

В `WorldManager` хранятся:

```gdscript
var world_width: int = 200
var world_height: int = 100
var seed: int = 0

# Размер чанка (константа)
const CHUNK_SIZE: int = 16

# Ссылка на менеджер чанков (Autoload)
var chunk_manager: ChunkManager

# Словарь всех чанков мира (ключ - Vector2i(chunk_x, chunk_y), значение - ChunkData)
var chunks: Dictionary = {}

# Ссылки на TileMapLayer (для рендеринга)
@onready var tilemap_light: TileMapLayer
@onready var tilemap_dark: TileMapLayer

var current_macro_biome: MacroBiome = MacroBiome.LIGHT   # enum { LIGHT, DARK }
```

**Примечание:** массива `tile_map` больше нет. Все данные хранятся исключительно в чанках. Операции с картой производятся через `ChunkManager`.

## 3. Алгоритмы генерации (поэтапно)

Генерация выполняется асинхронно с отображением прогресса. Каждый этап получает процент выполнения и обновляет UI. На каждом этапе все изменения тайлов записываются через `ChunkManager.set_tile(x, y, tile_id)`.

### Этап 1: Инициализация и базовый рельеф

- **Цель:** Создать чанки, заполнить их воздухом, сгенерировать высоту поверхности.
- **Алгоритм:**
  1. Создать все чанки (по сетке `ceil(width/CHUNK_SIZE) × ceil(height/CHUNK_SIZE)`) и инициализировать их тайлами `AIR`.
  2. Создать `FastNoiseLite` (тип `TYPE_OPEN_SIMPLEX_2`, частота 0.03, амплитуда 12).
  3. Для каждого X (0..width-1):
     - `height = noise.get_noise_2d(x * 0.1, seed_offset)`
     - `surface_y = base_y + round(height)`, где `base_y = 20`.
     - Для Y от 0 до surface_y-1: `set_tile(X, Y, AIR)` (оставляем пустым).
     - На `Y = surface_y`: `set_tile(X, Y, GRASS)`.
     - На `Y = surface_y+1` … `surface_y+3`: `set_tile(X, Y, DIRT)`.
     - На `Y = surface_y+4` … `world_height-1`: `set_tile(X, Y, STONE)`.
- **Прогресс:** 0–20%.

### Этап 2: Генерация пещер (Cellular Automata)

- **Цель:** Создать сеть пещер в подземной зоне (Y от 50 до 85).
- **Алгоритм:**
  1. Инициализировать 2D-булевый массив `cave_map` размером `width × 36` (только нужный диапазон).
  2. Заполнить случайно: для каждой клетки с вероятностью 45% - `true` (стена), иначе `false` (пустота) - только в заданном диапазоне Y.
  3. Применить 5 итераций Cellular Automata с правилом:
     - Если у клетки ≥ 5 соседей (из 8) - стена (`true`), иначе пустота (`false`).
  4. После итераций пройти по карте и для клеток `true` установить в чанках `STONE`, для `false` - `AIR`.
  5. **Связывание пещер:** найти все компоненты связности пустот (BFS). Для каждого компонента, кроме самого большого, проложить туннель к нему от ближайшей клетки большого компонента с помощью алгоритма Брезенхэма (прямая линия), заменяя стены на `AIR` по пути.
- **Прогресс:** 20–50%.

### Этап 3: Размещение руды (COPPER_ORE)

- **Цель:** Разместить медную руду в пещерах (Y ≥ 60) в виде небольших жил.
- **Алгоритм:**
  1. Использовать `FastNoiseLite` (другой seed) с частотой 0.1.
  2. Для каждой клетки (X, Y) в диапазоне Y ≥ 60 и Y < 85, где текущий тайл - `STONE` (не пустота):
     - Получить значение шума `noise_val`.
     - Если `noise_val > 0.7` и `randf()` < `biome.ore_density` (из BiomeData):
         - Размер жилы = `randi_range(min_cluster_size, max_cluster_size)`.
         - В случайном направлении (или по спирали) заменить указанное количество соседних `STONE` на `COPPER_ORE` (с проверкой границ).
- **Прогресс:** 50–65%.

### Этап 4: Размещение деревьев

- **Цель:** На поверхности на блоках `GRASS` разместить деревья с заданной плотностью.
- **Алгоритм:**
  1. Для каждого X от 0 до width-1 найти верхний блок `GRASS` (первый сверху).
  2. Если там `GRASS` и `randf()` < `biome.tree_density`:
     - Ствол: 4–5 блоков вверх от `GRASS` (заменить `AIR` на `WOOD`), проверяя, чтобы не выйти за верхнюю границу.
     - Листва: вокруг ствола (квадрат 3×3 или форма кроны) - заменить `AIR` на `LEAVES`.
- **Прогресс:** 65–80%.

### Этап 5: Размещение разломов (Rifts)

- **Цель:** Разместить 3 разлома в пещерах (только там, где есть пустое пространство).
- **Алгоритм:**
  1. Собрать все координаты (X, Y) в пещерах (Y ≥ 50, Y < 85, тайл == AIR).
  2. Выбрать 3 случайные позиции, расстояние между которыми ≥ 40 блоков (параметр настраиваемый).
  3. В этих позициях установить специальный маркер (например, сохранить в список `rift_positions`). Позже на этих местах будут созданы объекты-разломы.
- **Прогресс:** 80–90%.

### Этап 6: Финальная обработка и применение к TileMapLayer

- **Цель:** Отобразить сгенерированные чанки в обоих `TileMapLayer`.
- **Алгоритм:**
  1. Для каждого чанка в `chunks`:
     - Для каждой локальной ячейки (lx, ly) в чанке получить глобальные координаты (x, y) и `tile_id`.
     - Если `tile_id != AIR`:
         - Вычислить координаты атласа для светлого и темного вариантов (используя `get_atlas_coords_for_tile(tile_id, macro)`).
         - Установить ячейку в `tilemap_light` и `tilemap_dark`.
  2. Сделать видимым только текущий макробиом.
- **Прогресс:** 90–100%.

## 4. Работа с макробиомами и двумя TileMapLayer

### 4.1. Хранение

- Единые данные в чанках (массив `tiles` размером 256).
- Два узла `TileMapLayer` в сцене мира:
  - `TileMapLight` - использует `TileSet` со светлыми текстурами.
  - `TileMapDark` - использует `TileSet` с темными текстурами.

### 4.2. Обновление блоков

При разрушении/установке блока (из любого макробиома) вызывается единая функция:

```gdscript
func set_tile(x: int, y: int, tile_id: int) -> void:
    # 1. Обновляем данные в чанке через ChunkManager
    chunk_manager.set_tile(x, y, tile_id)
    
    # 2. Обновляем визуальное отображение в обоих слоях
    var coords = Vector2i(x, y)
    var atlas_light = get_atlas_coords_for_tile(tile_id, MacroBiome.LIGHT)
    var atlas_dark = get_atlas_coords_for_tile(tile_id, MacroBiome.DARK)
    tilemap_light.set_cell(coords, 0, atlas_light)
    tilemap_dark.set_cell(coords, 0, atlas_dark)
    
    # 3. Чанк помечается как dirty внутри ChunkManager.set_tile()
```

Функция `get_atlas_coords_for_tile(tile_id, macro)` должна быть реализована в `WorldManager` и возвращать корректные координаты атласа в зависимости от типа тайла и макробиома.

### 4.3. Переключение макробиома

```gdscript
func switch_macro_biome(new_macro: MacroBiome) -> void:
    current_macro_biome = new_macro
    tilemap_light.visible = (new_macro == MacroBiome.LIGHT)
    tilemap_dark.visible = (new_macro == MacroBiome.DARK)
    # Дополнительно: обновить освещение, атмосферу, спавн врагов и т.д.
```

### 4.4. Генерация обоих макробиомов сразу

При генерации мы заполняем оба слоя одними и теми же тайлами, но с разными атласами (этап 6). Изменения блоков также синхронно отражаются в обоих слоях.

## 5. Чанки (Chunks) - основа масштабирования

### 5.1. Размер и структура чанка

- **Размер:** 16×16 тайлов (константа `CHUNK_SIZE = 16`).
- **Данные чанка:** массив `int` размером 256 (индексация: `y * CHUNK_SIZE + x`).
- **Класс `ChunkData`** (наследует `RefCounted`):

```gdscript
class_name ChunkData
extends RefCounted

var position: Vector2i        # координаты чанка в сетке чанков
var tiles: PackedInt32Array   # 256 элементов, инициализируется AIR (0)
var is_dirty: bool = false    # изменен ли с момента последнего сохранения

func _init(pos: Vector2i) -> void:
    position = pos
    tiles.resize(CHUNK_SIZE * CHUNK_SIZE)
    tiles.fill(TileID.AIR)
```

- **Хранение в `WorldManager`:** словарь `chunks: Dictionary[Vector2i, ChunkData]`.

### 5.2. Менеджер чанков (`ChunkManager` - Autoload)

Обязанности:

- Предоставлять методы `get_tile(x, y) -> int` и `set_tile(x, y, tile_id)`.
- Внутри вычислять чанк и локальные координаты.
- При `set_tile` обновлять массив `tiles` в нужном чанке и выставлять `is_dirty = true`.
- В MVP загружать все чанки мира сразу (при создании или загрузке).
- Поддерживать получение всех чанков для сохранения.

### 5.3. Работа с чанками в MVP

- При генерации мира: `ChunkManager` создает все чанки, заполняет их `AIR`, затем генератор поэтапно заполняет их через `set_tile`.
- При загрузке сохранения: `SaveManager` восстанавливает все чанки из файла и регистрирует их в `ChunkManager`.
- При изменении блока (игрок или внешние системы) - всегда вызывается `ChunkManager.set_tile`, что гарантирует обновление данных и пометку чанка как dirty.
- Визуальные слои (`TileMapLayer`) обновляются отдельно (см. раздел 4.2) на основе измененного чанка (можно подписаться на сигнал `chunk_updated`).

### 5.4. Производительность и память

- Количество чанков для мира 200×100: `ceil(200/16) × ceil(100/16) = 13 × 7 = 91` чанк.
- Каждый чанк занимает в памяти 256 × 4 байта = 1024 байта + накладные расходы.
- Все чанки загружены в память (для MVP допустимо). При увеличении мира можно внедрить стриминг.

## 6. Сохранение и загрузка мира

### 6.1. Структура файла сохранения (бинарный)

```
[Header]
  version: uint32
  seed: uint32
  world_width: uint16
  world_height: uint16
  player_macro: uint8 (0=Light, 1=Dark)
  player_position_x: float
  player_position_y: float

[Chunk Data]
  count_chunks: uint32                  # общее количество чанков (всегда все)
  для каждого чанка:
      chunk_x: int16
      chunk_y: int16
      tiles_compressed: PackedByteArray # сжатый массив из 256 int (zlib)

[Inventory Data]
  # сериализованный InventoryData (используется стандартный ResourceSaver)
```

**Сжатие:** применяется `zlib_compress()` ко всему массиву `tiles` (256 элементов, каждый по 4 байта). При загрузке - `zlib_decompress()`.

### 6.2. Загрузка

1. Открыть файл, прочитать заголовок.
2. Восстановить параметры мира (размер, сид).
3. Прочитать все чанки, распаковать их и зарегистрировать в `ChunkManager`.
4. Заполнить оба `TileMapLayer` на основе данных из чанков.
5. Восстановить позицию игрока, макробиом, инвентарь.
6. Применить переключение макробиома.

### 6.3. Сохранение

- Вызывается при выходе из игры или по таймеру (автосохранение).
- Собирает все чанки из `ChunkManager` (или только dirty, но для MVP можно все).
- Сериализует заголовок и чанки в бинарный файл.
- Инвентарь сохраняется отдельно через `ResourceSaver` (интегрируется в тот же файл или отдельно - решается на уровне `SaveManager`).

## 7. Критерии приемки MVP генерации

1. **Детерминизм:** при одинаковом сиде мир идентичен (после генерации).
2. **Связность:** пещеры соединены (нет изолированных карманов).
3. **Ресурсы:** на поверхности есть деревья, под землей - медь, мир ограничен камнем снизу.
4. **Разломы:** ровно 3, только в пещерах, расстояние между ними ≥ 40 блоков (параметр настраивается).
5. **Переключение макробиомов:** визуально меняются текстуры, но география блоков остается той же.
6. **Изменения блоков:** разрушение/установка синхронно отражаются в обоих макробиомах (через `set_tile`).
7. **Производительность:** генерация занимает не более 2.0–3.5 секунд для маленького мира.
8. **Прогресс-бар:** отображается с сообщениями на каждом этапе.
9. **Сохранение/загрузка:** мир восстанавливается полностью (карта, инвентарь, позиция).
10. **Дебаг-инструменты:** отображение сида, координат, текущего макробиома, биома, глубины; регенерация с новым сидом; ручной ввод сида.

## 9. Технические заметки

- Использовать `@tool` для возможности тестирования генерации в редакторе.
- Для шума использовать `FastNoiseLite` с разными seed для разных этапов (высота, пещеры, руды).
- `ChunkManager` должен быть загружен как Autoload (вместе с `WorldManager`).
- При сохранении инвентаря использовать `ResourceSaver.save` (уже реализовано в инвентарной системе).
- Все изменения тайлов в чанках автоматически помечают чанк как `dirty` для последующего сохранения.

## 10. Дополнительные возможности (вне MVP, но заложены в архитектуре)

- Генерация структур (данжи, подземные дома, большие деревья).
- Поддержка новых биомов через добавление `.tres` в папку `resources/biomes/`.
- Мультиплеер: сервер хранит чанки и рассылает изменения.
- Стриминг чанков при движении игрока (частичная загрузка/выгрузка).
- Оптимизация: хранение только dirty-чанков при сохранении (уже заложено флагом `is_dirty`).
