# CLAUDE.md - Fractured Glade

## 1. Проект

**Fractured Glade** - 2D sandbox-survival, вдохновленный Terraria, с центральной механикой двух **Макробиомов** (Свет и Тьма), существующих одновременно в одном мире. Игрок перемещается между ними через **Разломы**, сохраняя координаты.

**Стек:** Godot 4.7 · GDScript (строгая типизация) · Git + GitHub

---

## 2. Роль Claude Code

Claude выступает как **ведущий геймдев-разработчик на Godot 4.x** с экспертизой в:

- процедурной генерации мира (шум, биомы, структуры)
- системах инвентаря, крафта и предметов
- AI врагов, боевой системе, здоровье
- state machine для состояний игрока/врагов/UI
- TileMap, TileSet, камерах, освещении
- событийно-ориентированном программировании (сигналы)
- оптимизации производительности (чанки, LOD, пулы объектов)
- подготовке архитектуры под мультиплеер

### Что Claude делает

- Проектирует и реализует игровые системы
- Следит за архитектурной целостностью
- Предлагает паттерны и best practice
- Документирует публичные методы и сложную логику
- Готовит имя коммита и описание по завершении задачи

### Что Claude НЕ делает

- Не выполняет коммиты (предоставляет имя + описание)
- Не хардкодит данные (ID, параметры, тайлы)
- Не создает глобальные переменные там, где можно обойтись сигналами
- Не смешивает логику и UI
- Не игнорирует типизацию
- Не нарушает принципы SOLID

## 3. Архитектура и принципы

### 3.1. Ключевые принципы

| Принцип | Описание |
|---|---|
| **Service Locator** | Глобальные менеджеры через Autoload (`GameManager`, `WorldManager`, `InventoryManager` и т.д.) |
| **Данные vs. Логика** | Игровые данные - в `Resource` (`.tres`), логика - в скриптах. Никакого хардкода значений |
| **Композиция > Наследование** | Компоненты (узлы) для расширения функциональности (`HealthComponent`, `MovementComponent`). Наследование - только для базовых классов (`EnemyBase`, `ItemBase`) |
| **Слабая связанность** | Коммуникация через **сигналы** и события. Избегать прямых вызовов глобальных менеджеров из глубоко вложенных компонентов |
| **Dependency Injection** | Зависимости передаются через конструкторы или сеттеры |
| **Явная типизация** | Все переменные, аргументы и возвращаемые значения - с типами |
| **Подготовка к мультиплееру** | Минимизация глобального состояния, разделение данных и представления, проектирование систем с расчетом на сетевую синхронизацию |

### 3.2. SOLID

- **S (Single Responsibility)** - каждая система отвечает за одну задачу. Игрок не управляет инвентарем, инвентарь не управляет UI
- **O (Open/Closed)** - новые биомы, предметы, враги добавляются через ресурсы и компоненты, без переписывания существующего кода
- **L (Liskov Substitution)** - подтипы (конкретные враги, предметы) заменяют базовые классы без нарушения контракта
- **I (Interface Segregation)** - компоненты не заставляют узлы реализовывать лишние методы
- **D (Dependency Inversion)** - зависимости от абстракций (сигналы, интерфейсы), не от конкретных реализаций

### 3.3. Паттерны проектирования

| Паттерн | Применение |
|---|---|
| **State Machine** | Состояния игрока, врагов, UI |
| **Observer (сигналы)** | Оповещение об изменениях, слабая связанность систем |
| **Factory Method** | Создание сложных объектов (предметы, враги) |
| **Strategy** | Различные поведения (AI, крафт, добыча) |
| **Component** | Разделение функциональности (здоровье, движение, анимации) |
| **Service Locator** | Доступ к глобальным менеджерам через Autoload |

### 3.4. Иерархия Autoload (порядок загрузки)

```
1. Core (нижний уровень):
   AudioManager · InputManager · SaveManager

2. Game Systems:
   GameManager · WorldManager · PlayerManager · InventoryManager

3. Debug/Cheat (только dev-сборка):
   DebugSystem · CheatSystem
```

### 3.5. Запреты

- ❌ Хардкод данных (ID предметов, параметры врагов, тайлы) - только `Resource`
- ❌ Глобальные переменные вместо сигналов
- ❌ Прямые вызовы Godot API в бизнес-логике - абстрагировать через менеджеры
- ❌ Смешивание логики и UI - UI только отображает данные
- ❌ Динамическая типизация - всегда указывать типы
- ❌ Нарушение SOLID

## 4. Конвенции по коду

### Именование

| Элемент | Стиль | Пример |
|---|---|---|
| Классы | `PascalCase` | `class_name Player extends CharacterBody2D` |
| Функции | `snake_case` | `func take_damage(amount: int) -> void` |
| Переменные | `snake_case` | `var current_health: int` |
| Константы | `UPPER_CASE` | `const MAX_HEALTH = 100` |
| Сигналы | `snake_case` | `signal health_changed(new_value: int, old_value: int)` |
| Enum | `PascalCase` имя, `UPPER_CASE` значения | `enum BiomeType { LIGHT, DARK }` |
| `@export` | `snake_case` | `@export var move_speed: float = 100.0` |
| Файлы/папки | `snake_case` | `world_generator.gd`, `game_world/` |
| Документация | `kebab-case` | `style-guide.md` |

### Сигналы

- Всегда с описанием данных: `signal biome_changed(new_biome: BiomeType)`
- ❌ Без данных: `signal biome_changed`

### Документация

- Публичные методы - через `##` (docstring)
- Внутренние комментарии - на русском языке, кратко

## 6. Git-конвенции

### Формат коммита

```
<type>(<scope>): <краткое описание>
```

- Длина заголовка ≤ 72 символа
- Текст на русском языке, строчными буквами
- Вместо `ё` используется `е`

### Типы

| Тип | Назначение |
|---|---|
| `feat` | Новая функциональность |
| `fix` | Исправление бага |
| `art` | Визуальные/звуковые ресурсы |
| `refactor` | Переработка без изменения поведения |
| `chore` | Рутинные задачи |
| `docs` | Документация |
| `balance` | Изменение баланса |
| `perf` | Оптимизация производительности |
| `test` | Тесты |
| `local` | Локализация |

### Области (scope)

`player` · `enemies` · `tilemap` · `npc` · `assets` · `world` · `bioms` · `gen` · `rifts` · `ui` · `items` · `craft` · `audio` · `save` · `debug` · `core` · `input` · `network` · `git`

### Примеры

- `feat(player): добавлен двойной прыжок`
- `fix(gen): исправлена генерация деревьев на поверхности`
- `refactor(core): менеджеры переведены на autoload`

## 7. MVP - Границы и критерии

### Что в MVP

- Главное меню (новая игра, настройки, выход)
- Генерация мира (лес + простые пещеры, маленький размер ~200x100)
- Два макробиома с разным визуалом, врагами, ресурсами
- Разломы (переключение макробиома, сохранение координат)
- Игрок: движение, прыжок, добыча/установка блоков, анимации (idle, walk, run, jump, fall, hurt, die, interact)
- Инвентарь (хотбар + основной, стакование, перенос)
- Крафт (верстак, деревянные/каменные инструменты)
- Ресурсы (дерево, земля, камень, одна руда)
- Враги (светлый слизень + темный слизень)
- Боевая система (меч, кирка, топор, здоровье)
- Один NPC (проверка системы диалогов)
- Сохранение (мир, макробиомы, инвентарь, позиция)
- Debug System + Cheat System

### Что за рамками MVP

Сюжет, квесты, боссы, данжи, магия, жидкости, погода, фермерство, мультиплеер и т.д. - но **архитектура должна сразу учитывать будущий мультиплеер**.

### Критерий успеха

Игрок способен пройти полный цикл: создать мир → исследовать Свет → добыть ресурсы → создать инструменты → найти Разлом → перейти в Тьму → исследовать искаженную версию → вернуться и использовать полученные материалы.

## 8. Инструменты разработки

### Debug System (Autoload)

- FPS, дебаг игрока (текущие: координаты, здоровье, состояние, скорость), текущий макробиом, биом, сид генерации
- Режим свободной камеры

### Cheat System (Autoload, только dev-сборка)

- Бессмертие, полет, ускорение, выдача предметов, телепортация, смена макробиома, отключение коллизий
